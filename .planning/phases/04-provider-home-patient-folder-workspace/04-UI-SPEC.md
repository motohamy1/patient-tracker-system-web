# Phase 4 — UI Design Contract (Provider Home + Patient Folder Workspace)

> Visual and interaction contract for the provider-home surfaces. Generated by the phase UI
> research pass, verified against `docs/governance/reference-ui-specification.md` §4 and the
> binding reference `docs/reference/provider-home-primary.jpg` (inspected this session).
> Downstream consumers: the planner (surfaces, primitive reuse, copy), the executor (visual
> source of truth), the phase-close visual gate.

## 0. Scope, authority and reading order

**Authority.** `docs/governance/tokens.json` is the frozen value source — restated here by token
name only, never by value. `docs/governance/ui-invariants.md` (`INV-01`…`INV-17`),
`docs/governance/visual-qa-rules.md` (rows 1…12) and `docs/governance/reference-ui-specification.md`
§4/§7 outrank this document wherever they disagree. The Phase 2 contract (`02-UI-SPEC.md`) and the
Phase 3 contract (`03-UI-SPEC.md`) remain binding for every primitive and shell rule they declare;
this document **extends** them, it does not relax them.

**What this phase builds visually — and only this.**

| # | Surface | Introduced because |
|---|---------|--------------------|
| 1 | Provider Home folder grid body at `/provider` (replaces the Phase-2 empty shell body) | PROV-01; the hero interaction of the phase |
| 2 | Folder card (identity, status encoding, last activity, contextual indicators) | PROV-03 |
| 3 | Retrieval filter tabs (All / Recent / Today / Needs attention / Critical) above the grid | PROV-02, D-11 |
| 4 | Server-side search wired from the existing top-bar `CompactControl search` (300ms debounce) | PROV-02, D-17/D-18 |
| 5 | New-patient modal form (Overlay, core identity fields) | PROV-04, D-02/D-05 |
| 6 | Folder-card quick-actions surface (change status, send invite, schedule placeholder) | PROV-04, D-15 |
| 7 | "Load more" pagination control + per-filter empty states | UX-07, D-20 |
| 8 | Provider-home primary CTA enabled (`accentSoft` gold) | D-16; Phase 2 shipped it `disabled` pending this phase |

**What this phase does not build.** Any clinical table content (visits, medications, labs, imaging,
allergies, genetics), the patient workspace body (Phase 5), the timeline (Phase 6), appointment
widgets (Phase 7), patient-side surfaces (Phase 13), any Critical-Alerts or Daily-Stats panel
(their data does not exist until clinical events do — the reference panels are **layout grammar
for later phases**, not this phase's scope), dense list view, virtualization. No specialty label
appears anywhere (§3.3, §27). The eight workspace tabs and all existing routes are untouched.

**Route placement.** Everything lives at the existing `/provider` route (02-CONTEXT D-01/D-02 route
map is locked). The new-patient form is a modal over that route, never a new path. Quick actions are
an overlay over the grid. No new top-level path exists.

No raw color value appears in this file. Every color below is a token name; the value lives in
`docs/governance/tokens.json`.

**Status encoding (D-10 — the concrete rule).** Exactly five statuses, mapped once:

| Status | Token | Label text |
|--------|-------|-----------|
| `stable` | `success` | "Stable" |
| `follow_up` | `warning` | "Follow-up" |
| `needs_review` | `info` | "Needs review" |
| `critical` | `critical` | "Critical" |
| `new` | `info` | "New" |

Rules: the status appears in exactly two places per card — a **thin 2px status line** (see Reviewer
item R-2) running under the card header, and one **`Pill`** whose tone paints only its leading dot
(the `Pill` primitive's grammar; label ink is always `textPrimary`). No folder body, background or
name is ever tinted. Never one saturated color per folder (§5; D-10 cites Phase 1 D-04).

`Pill` tone extension: `critical` is added as a fifth `PillTone` value. `Pill.tsx`'s comment
requires a recorded decision for any tone beyond `success/info/warning/neutral` — **D-10 of this
phase is that record**. Reviewer item R-1 below flags the INV-04 letter at the owner gate.

Accent reserved for (this phase): the primary CTA (`accentSoft`) only. `accent` proper appears
nowhere new (INV-05).

## Surface Specs

### 4.1 Provider Home body — folder grid (PROV-01, PROV-03)

**Outer structure (§4 grammar, adapted honestly).** The Phase-2 shell already supplies the left icon
rail (`frame`), the top bar (pill search, gold CTA, bell, profile) and the mobile nav. This phase
fills the body: a **folder grid region** on `canvas` directly under the top bar, with the retrieval
control row above it. The reference's left "Today's Schedule" rail and right "Critical Alerts"/
"Daily Stats" panels are NOT built — no appointments (Phase 7) and no clinical events exist yet;
inventing their content would violate FOUND-01 (no fake clinical content) and §27. The grid
therefore occupies the body width with a comfortable max width and generous `canvas` margins.

**Grid.** `3 columns` at ≥1024px (QA row 5), `2 columns` at 768–1023px, `1 column` below 768px
(responsive-rules bands). Gap `space.lg`. The grid is the main patient-discovery interaction and
search/filter coexist with it (§5): the control row sits **above** the grid, never on a separate
page or view (D-12).

### 4.2 Folder card (PROV-03)

Anatomy, top to bottom — `Surface variant="surface"` on `canvas`, `radius.lg`, `shadow.raised`,
**no border** (INV-15/INV-16), floating on canvas:

1. **Folder tab silhouette** — a small centered/notched tab detail on the top edge, rendered from the
   same `surface` fill and `radius.sm` on its outer corners (pure CSS, no new shadow). This is the
   "premium digital clinical folder" signature (§5: folders must resemble premium digital clinical
   folders). Restrained: no gloss, no skeuomorphic texture.
2. **Header row** — patient full name (Heading, 600) with the MRN beneath in Label type
   (`textSecondary`), plus a three-dot quick-actions button (`iconOnly`, `ariaLabel` "Actions for
   {name}") at the trailing edge. Where an avatar image does not exist, a `surfaceMuted` rounded
   initial disc (name initials, Label type) — never a stock photo, never a colored avatar.
3. **Status line** — full-width 2px line in the D-10 token (`rounded-pill` ends), sitting under the
   header. The single strongest scan cue on the card (reference: "thin horizontal strip").
4. **Identity line** — "42 · F" (age from DOB at render time, `tabular-nums`) — minimal age/sex per
   PROV-03. Phone and DOB are NOT printed on the card (minimization); they live in search + the
   workspace.
5. **Footer** — "Last activity" Label in `textSecondary` + the absolute date (`tabular-nums`), and at
   most one small contextual indicator (16px glyph): e.g. an unlinked-account glyph when `user_id`
   is null (this is what "Send invite" acts on), a `critical`-family warning glyph for `critical`
   status rows. Small, `textSecondary` ink except the glyph itself.

Clicking anywhere on the card (excluding the quick-actions button) opens the patient workspace
(`/provider/patients/[patientId]`) — the workspace shell exists since Phase 2 (PROV-01's "opens the
patient's workspace on interaction"; its body fills in Phase 5).

Card height stays compact — no card holds one line of content or fewer (INV-12); the card is roughly
the reference folder's density: five tight rows.

### 4.3 Retrieval controls (PROV-02, D-11/D-12)

A single row above the grid, left-aligned: **`SegmentedControl`** (the label-only `TabBar` variant,
`INSET_FILL` container) with items `All | Recent | Today | Needs attention | Critical`, `value`
bound to the active filter, `onValueChange` → URL state. Active item is the raised pill treatment
already defined by `TabBar`. This is the §4 "pop-out filter panel" grammar resolved to pill tabs
(04-CONTEXT: "must use the `TabBar` or `Pill` primitive … follow the pill-control grammar").

Trailing on the same row: a compact result count ("24 patients", Label, `tabular-nums`,
`textSecondary`) — the honest answer to "what am I looking at" when a filter is active.

Mobile: the tab row scrolls horizontally (`[scrollbar-width:none]` already in the primitive); every
tab keeps its 44px touch target (responsive-rules).

### 4.4 Search (PROV-02, D-17/D-18)

The existing top-bar `CompactControl variant="search"` (`label="Search patients"`, `inputId` bound)
becomes live: a thin client wrapper debounces `onValueChange` at **300ms** and writes `?q=` into the
URL (`router.replace`, `scroll: false`). No local filtering ever happens (D-18). The search box is
present on all breakpoints (Phase 2 hid it `max-md:hidden`; this phase restores it on mobile in the
body control row instead — see 4.7 — while the desktop top bar keeps it).

### 4.5 New-patient modal (PROV-04, D-02/D-05/D-06/D-07/D-08)

The primary CTA (`Button variant="primary"` — `accentSoft` pill with a leading 16px glyph and
`textPrimary` ink) reads **"Add new patient"** (D-16; §7 contract: single verb + noun, sentence
case). It lives in the top bar where Phase 2 placed it (now enabled) and, on mobile, as a floating
primary action in the body control row.

Form fields, in order (03-UI-SPEC §8.1's form grammar: `radius.md` inset fields, `surfaceMuted`
fill via `INSET_FILL`, programmatic labels, one shared height rhythm):

1. First name (text, required)
2. Last name (text, required)
3. Date of birth (date, required; must be in the past)
4. Sex (segmented `M | F` — D-08; radios or `SegmentedControl`, pill grammar)
5. Phone (tel, required)

The MRN is **not** a field: a single `textSecondary` helper line under the form states "The medical
record number is assigned automatically." (D-07 — the provider never types it).

Footer: `Button primary` "Add patient" + `Button ghost` "Cancel". On success the modal closes and
the grid shows the new card (D-06 — no navigation away); validation errors render inline under the
field (Zod `flattenError` mapping, 03-UI-SPEC focus rules: error text `critical`-family ink is NOT
used — errors are a `critical` dot + `textPrimary` message, per the Pill dot grammar; the message
text carries the meaning).

Title: "Add new patient". No exclamation marks anywhere (§7).

### 4.6 Quick actions surface (PROV-04, D-15)

The three-dot button opens the **`Overlay`** (modal ≥1024px / sheet below — the Phase-2 primitive
with its full a11y contract; no popover primitive is introduced). Title: "{patient name}". Rows,
each a full-width 44px action row (`radius.md`, `surfaceMuted` hover via `surfaceRaised`… no new
hover token — hover = `surfaceRaised` fill):

1. **Change status** — expands inline (or a second sheet step) to the five statuses as pill choices;
   selecting one calls the status action and closes. Current status is indicated by its `Pill`
   treatment and `aria-current`.
2. **Send invite** — only when `user_id` is null AND the resolved role holds `CAN_MANAGE_MEMBERSHIP`
   (server-known; hidden entirely otherwise — no dead control). Calls the invite action linked to
   this patient (D-04); the overlay swaps to a confirmation state showing the invite link with a
   copy button (03-UI-SPEC §8.3's invite-link display grammar).
3. **Schedule appointment** — renders **disabled** with `aria-disabled="true"` and a trailing
   `textSecondary` note "Available with scheduling" (04-CONTEXT discretion: it must not look like a
   working feature if it does nothing). It never opens anything and is never a dead *enabled* button
   (the repo's hard rule is no dead enabled controls; a disabled future affordance with an honest
   note is the sanctioned form).

Open workspace is the card click itself (4.2), not a row.

### 4.7 Pagination, empty and state variants (UX-07, D-20)

- **Load more** — a `Button variant="secondary"` pill centered under the grid, labeled "Load more";
  hidden when no further page exists. The result count in 4.3 reflects what is loaded vs total
  ("24 of 137 patients") when more pages remain.
- **Empty states** — `EmptyState` per filter (04-CONTEXT discretion resolved):
  - All: **"No patients yet"** / "Patient folders appear here once they are added to the practice." (the exact Phase-2 §9.1 copy — reuse, do not rewrite) + action "Add new patient" wired to the modal.
  - Recent: "No recent activity" / "Patients appear here once their records change."
  - Today: "No patients today" / "Patients created or updated today appear here."
  - Needs attention: "No patients need attention" / "Patients marked for follow-up or review appear here."
  - Critical: "No critical patients" / "Patients marked critical appear here."
  - Search with no matches: "No matching patients" / "Try a different name, record number, phone number or date." (never leak which field failed to match)
- **Loading** — `LoadingSkeleton` grid of folder-shaped skeletons (3/2/1 per breakpoint), never a
  generic "Loading…" (§7, UX-01).
- **Error** — `StateVariant` with retry wired to `router.refresh()`; copy per §7: "Couldn't load
  patients. Check your connection and try again." + "Try again".
- **Permission denied / offline** — inherited unchanged (03-UI-SPEC §8.4/§8.6).
- **Mobile search** — the search control repeats in the body control row below 768px (the top-bar
  one stays `max-md:hidden` as Phase 2 set it).

## Focus and Keyboard (inherited, bind where new)

- Folder cards are links (or `role="link"` reachable by Tab); the quick-actions button is the next
  tab stop after its card's link. Enter/Space on a card opens the workspace.
- The quick-actions Overlay traps focus (existing `useFocusTrap`) and restores focus to the invoking
  three-dot button on close.
- The filter `SegmentedControl` is a proper tablist per the `TabBar` primitive contract.
- Debounced search never traps focus or clears the field during typing.

## Contrast Findings and Reviewer Items

**R-1 — INV-04 letter vs D-10 (OWNER GATE, blocking).** INV-04's objective check limits status
encoding to `success`/`info`/`warning`; D-10 (locked this phase) maps `critical` status to the
frozen `critical` token. Rationale for implementing D-10: a critical patient must not wear
follow-up amber; `critical` is a frozen 15-key token, not a new tint family (which is what INV-04
actually forbids); the reference itself uses a `critical`-family surface on Provider Home. The
gate must adjudicate the letter of INV-04 — options: (a) accept D-10 and amend INV-04's objective
check wording to "a subset of success/info/warning/critical", or (b) reject and re-map `critical`
status to `warning` (rejected here on clinical-legibility grounds). **Nothing is silently changed
in governance docs.**

**R-2 — INV-11 letter vs the status line (OWNER GATE, non-blocking).** INV-11 caps rules/dividers/
axis lines at 1px; §4 binds "thin progress lines" and the reference bar renders ≈2–4px. This spec
declares the status line a **status indicator** (2px, `h-0.5`) rather than a rule/divider. Gate may
accept the classification or require 1px.

**R-3 — accent restraint check.** The only new accent-family element is the CTA (`accentSoft`,
INV-05's reserved list). A pixel-share pass over the rendered home must keep accent ≤10% (QA row 2/12).
