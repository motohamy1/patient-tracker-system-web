Why `page.evaluate(() => document.fonts.ready)` before asserting: font loading is the most common source of visual-regression flake, and unresolved fonts shift layout between the Windows dev machine and the Linux CI container.

Add the FND-02 runtime proof. The unit tests in Plan 01-02 only string-match `tokens.css`; nothing so far proves a token actually reached Tailwind as a utility AND reached the DOM as a CSS custom property. Assert both in the browser:

    test('tokens reach both Tailwind utilities and CSS custom properties', async ({ page }) => {
      await page.goto('/en/design-gallery');
      const resolved = await page.evaluate(() => {
        const probe = document.createElement('div');
        probe.className = 'bg-accent rounded-module bg-frame-olive shadow-module';
        document.body.appendChild(probe);
        const cs = getComputedStyle(probe);
        const out = {
          accentVar: cs.getPropertyValue('--color-accent').trim(),
          shadowVar: cs.getPropertyValue('--shadow-module').trim(),
          oliveVar: cs.getPropertyValue('--color-frame-olive').trim(),
          bg: cs.backgroundColor,
        };
        probe.remove();
        return out;
      });
      // CSS custom properties exist (FND-02, second half)
      expect(resolved.accentVar).toBe('#F2FE46');
      expect(resolved.oliveVar).toBe('#4F4F28');
      expect(resolved.shadowVar).not.toBe('');
      // Tailwind utilities exist and resolve (FND-02, first half)
      expect(resolved.bg).toBe('rgb(242, 254, 70)');
    });

`bg-accent` resolving to `rgb(242, 254, 70)` is the proof that `@theme static` produced a real utility AND a custom property from one declaration. `--shadow-module` being non-empty is the specific reason `@theme static` (not the default) is required.
