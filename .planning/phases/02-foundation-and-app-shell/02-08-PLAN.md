# Plan 02-08 — The provider route group: rail, top bar, workspace tabs, and eight empty shells

## Objective

Build the provider side of the shell: the persistent left icon rail, the provider top bar, the mobile pill strip, the workspace top bar, and every provider route as a correctly framed empty shell — including the eight workspace tabs as real nested routes.

Purpose: D-01 locks the URL map in this phase precisely so Phases 003 to 005 fill bodies instead of inventing paths. D-02 locks the chrome into route groups so no role's chrome can leak into the shared root layout. FOUND-01 then requires each of those routes to render with real typography and surface tokens rather than a structural placeholder, so the visual baselines have something to capture and no clinical data enters the tree.

Output: four shell components, one provider layout, and eleven route files.

## Empty-state copy (binding, from `02-UI-SPEC.md` §9.1)

| Route | Title | Body |
|---|---|---|
| `/provider` | "No patients yet" | "Patient folders appear here once they are added to the practice." |
| `/provider/patients/[patientId]` and each of its eight tabs | "No record yet" | "This patient's record fills in as visits, medications and results are documented." |

No route renders an action, because no destination is wired in this phase. No route names a patient, a medication, a measurement, a record number or a specialty (`docs/governance/reference-ui-specification.md` §9, `PRODUCT-MASTER-SPEC.md` §27).

| Route group nesting → document reload semantics | Whether one root layout exists determines whether a role switch is a client navigation; a second root layout would also be the natural place a later phase might be tempted to add a role-dependent guard. |
| Empty shells → shipped HTML | Each route renders static markup that reaches a browser, so any copy, label or identifier placed here becomes part of the shipped document. |
| Component tree → assistive technology | The rail and top bar are the shell's primary keyboard and screen-reader surfaces. |

## ASVS scope statement (recorded, not omitted)

**ASVS V2 Authentication and V3 Session Management were assessed and are NOT YET APPLICABLE to this plan.** No identity is resolved and no cookie or token is created or read here; those obligations belong to Phase 003.

**ASVS V4 Access Control is NOT YET APPLICABLE, and this plan carries one hard negative rule in consequence:** it creates **no** client-side gate of any kind and reads no role from anywhere client-held. All routes render openly by decision D-03, and the layout carries a comment marking exactly where Phase 003's **server-side** role resolution slots in. A fake gate that looks real is worse than none, and no `middleware.ts` is created.

**ASVS V5 Input Validation is assessed and is the one category that genuinely applies:** the `[patientId]` route parameter is attacker-controlled. Its discipline here is negative and absolute — it is never rendered, never passed to a query, a filesystem path, a shell, a template or a log, and is used only to build hrefs through `tabHref`. The eight tab pages each carry a comment recording this. **ASVS V6 Cryptography** is assessed in its negative form: no secret, key or credential appears in any file this plan writes.

**ASVS V8 Data Protection** applies: no clinical content may appear in the shipped markup. **ASVS V12 Files and Resources** does not apply — no upload, no user-supplied path, no `public/` content. **ASVS V14 Configuration** does not apply — no environment variable is read by these routes; the dev-gallery gate arrives in plan 02-10.
