# Plan 02-01 — D-27 re-sampling of `frame` and `surfaceMuted`, and the owner re-freeze

## Objective

Re-open the two color tokens the owner re-opened on 2026-10-06 (`CONTEXT.md` D-27) and re-sample them from the binding reference images so the four surface roles of the shell are visually distinct before any code is written.

At the frozen values `color.frame`, `color.surface` and `color.surfaceMuted` are byte-identical, so every `surfaceMuted` control the foundation ships — the compact search field, the icon-toggle off state, the `TabBar` container, the inset note field — renders with **no visible boundary** against its `surface` or `frame` parent, while `INV-15`/`INV-16` forbid the border that would create an edge and `INV-13` forbids the third shadow. The visual baseline for a primary interaction would capture an invisible control.

Purpose: the token layer is the input to a build-time codegen that no later phase can override. Once code exists, a token change ripples through every baseline. Re-sampling is therefore a Wave 1 prerequisite, not a cleanup.

Output: two re-sampled values written into `docs/governance/tokens.json` with full provenance, the governance prose swept, and the owner's visual re-review recorded — mirroring the D-08 gate that closed Phase 001.

## Non-goals (fence)

This plan writes exactly two files. It creates no `package.json`, no `src/`, no `.gitignore`, no config and no test. It does not re-sample the 13 other color tokens, and it does not decide any of them.

## Tooling precondition — read this before sampling

`ffmpeg` is the sampling tool Phase 001 used and it **is** present on this workstation (8.1.1, resolved through WinGet; `ffmpeg -version` and `ffprobe -version` both succeed). Run both once at the start of task 1 and record the version.

**If `ffmpeg` is unavailable at execution time:** do **not** invent values, do not fall back to a color picker, and do not write a plausible-looking hex into `tokens.json`. Instead:

1. Stop and report the blocker with the exact shell error.
2. Apply the documented Phase 001 fallback order (`01-PLAN.md` task-2): (a) PowerShell `System.Drawing` pixel read of a cropped region; (b) if that is also unavailable, a manual eyedropper read on a magnified crop.
3. A value produced by fallback (a) is admissible **only** because it is the same region-average arithmetic; record `"method": "System.Drawing region-average (crop WxH+X+Y, area-average, rgb24)"` in `provenance.tokens[n].method` and set `visionEstimate: true`.
4. A value produced by fallback (b) — or any value the executor proposes without a passing sub-scan and agreement gate — is **not** admissible under D-27. The correct action is to present the candidate to the owner as a documented approximation in the D-27 owner gate, with the fallback method recorded, and let the owner accept or reject it. Approval by the owner is what makes it admissible; executor judgement alone never does.

## Method (binding, identical to `docs/governance/reference-ui-specification.md` section 3.16)

For each of the two tokens, in this order:

1. Locate the region by eye, then confirm numerically.
2. Place at least five **disjoint** windows per token, each 8 to 24 px on a side, each at least 12 px from any text, icon, card edge, divider, gradient boundary or node boundary, and at least 4 px from every other window of the same token.
3. Read each window with `ffmpeg -v error -i <img> -vf "crop=W:H:X:Y,scale=1:1:flags=area,format=rgb24" -frames:v 1 -f rawvideo -pix_fmt rgb24 pipe:` piped into a `node -e` reader. The reader **must** print `bytes: 3`. Any other byte count means the crop or the filter chain is wrong; fix it before recording.
4. Reject any window whose 4x4 sub-scan spreads any channel by more than 4/255. Run the sub-scan with `scale=4:4:flags=area,format=rgb24` (48 bytes = 16 pixels); the spread is max minus min per channel.
5. Re-sample each accepted window shifted `+4` and `-4` px horizontally. Both shifted reads must agree with the unshifted read within 2/255 per channel. A window failing either gate is rejected and replaced.
6. The frozen value is the **channel-wise median** of the accepted windows, uppercase six-digit hex.

## Region anchors — how the two tokens stop being the same measurement

The reason the three tokens froze identically is that all three were sampled from the *same flat band*. Re-sampling the same band reproduces the same value. Each re-opened token must therefore be sampled from the region that actually plays its role in the reference:

- **`frame`** — structural chrome. Sample the provider-home left rail and top-bar band in `docs/reference/provider-home-primary.jpg`, cross-checked against the timeline top-bar band in `docs/reference/patient-workspace-timeline-primary.jpg`. A `crossChecks` entry of this kind already exists for `frame` and records the provider-home rail median; this plan replaces the primary windows with rail-anchored ones and keeps the cross-check, so the two structures can be compared rather than merged.
- **`surfaceMuted`** — inset panel fill. Sample a genuine inset region: the bottom scrubber capsule track in `docs/reference/patient-workspace-timeline-primary.jpg` and/or the quick-log note field in `docs/reference/patient-home-primary.jpg`, per `docs/governance/reference-ui-specification.md` sections 2.1 and 3.5, which name the scrubber track and the quick-log note field as the surfaces that own this token.

If the sampled medians for `frame` and `surfaceMuted` still land on the same value, or either still lands on `color.surface`, **do not proceed to task 2**. Report the measurement, keep the recorded evidence, and raise it at the owner gate in task 3 as a sampling-anchor failure — the correct resolution is a different region, not a nudge.
