# Plan 02-04 — The three machine checks: `no-raw-hex`, `no-generic-healthcare-blue`, `token-reference-required`

## Objective

Build the single zero-dependency Node script that enforces the three checks `docs/governance/project-constitution.md` §8 specifies, wire it into `lint` and `prebuild`, and prove it with fixtures that must fail and fixtures that must not.

Purpose: Phase 001 specified these three checks by name and wrote no implementation. Until this plan lands, "no raw hex" and "no generic healthcare blue" are review conventions; after it, they are build failures. Twenty later phases inherit the enforcement, which is why the utility vocabulary must be derived rather than typed.

Output: `scripts/check-design-tokens.mjs`, two unit-test files covering every check and the false-positive cases, and a green `npm run lint` over the current tree.

## The three checks (verbatim scope from the constitution, implemented as-is)

| Check | Scope | Failure |
|---|---|---|
| `no-raw-hex` | every source file under `src/`, plus the root configs, explicitly excluding the generated token layer | any raw color literal outside the generated token layer |
| `no-generic-healthcare-blue` | every source file including theme and config | a generic blue/indigo/violet/purple default-palette color in any styling location, which implements the `INV-01`/`INV-03` grep |
| `token-reference-required` | every component and layout file | component styling that does not reference the semantic token utilities |

Report `file:line`, the literal, the check name and `INV-03`.

Report `file:line` (line 1, since the condition is about the file), the file path, the check name and the two invariants it answers.

## Trust Boundaries

| Boundary | Description |
|---|---|
| Source files → static analyzer | The script reads arbitrary source text and judges it. A false positive erodes trust and will be silenced by a bypass; a false negative silently admits the exact violation the constitution forbids. |
| `docs/governance/tokens.json` → derived utility vocabulary | The presence check's correctness depends entirely on this derivation being complete and programmatic. |
| Analyzer output → build gate | A non-zero exit blocks `npm run lint` and `npm run build`; a developer under pressure may bypass the script rather than fix the violation. |
| Commit-time → pre-commit | Not applicable: no hook is installed, so nothing fires between commit and CI-less build. |

## ASVS scope statement (recorded, not omitted)

**ASVS V2 Authentication, V3 Session Management, V4 Access Control, V5 Input Validation and V6 Cryptography were assessed and are NOT YET APPLICABLE to this plan.** The script analyzes text files; it has no runtime, no user input, no session and no credential. The access-control obligations belong to Phase 003 (D-03).

**ASVS V8 Data Protection** applies in a narrow but real form: this is the mechanism that prevents a raw value or a hardcoded clinical string from entering shipped styling. **ASVS V10 Malicious Code** applies to the script's own supply chain, which is empty — it imports only `node:` builtins and one sibling module, so there is no third-party code in the gate that decides whether a build passes. **ASVS V14 Configuration** applies to the production guard, which reads `NODE_ENV` and fails closed when the generated token layer is absent. **ASVS V12 Files and Resources** does not apply — no upload, no user path, no executable content.
