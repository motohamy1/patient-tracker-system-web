# Phase 1 — UI Design Contract (Reference UI Specification)

> Visual and interaction contract for the project constitution phase. Generated by gsd-ui-researcher, verified by gsd-ui-checker. This is the **source contract** for the `docs/governance/` reference UI specification that Phase 1 execution materializes (per D-16); it is also the design source of truth that Phases 002–022 cite.

## 0. Phase Boundary — How To Read This Contract

This phase produces **governance documents and the frozen token JSON only**. It produces **no product code, no `tokens.css`, no components, no Playwright harness, no lint/CI implementation**. Consequences, binding on every consumer of this file:

1. **Token values live in a canonical `tokens.json`** (`name → value`, machine-readable — D-07). The CSS token layer (Tailwind v4 `@theme` + kebab-case custom properties) is **generated from the JSON in Phase 002** (D-10). This UI-SPEC *defines* the JSON contract; the Phase 1 plan *materializes* the JSON file.
2. **Every hex value below is provisional and carries a provenance note** (see §1.4). Exact values are finalized by pixel sampling during Phase 1 execution and **visually reviewed by the product owner at this phase's design gate, before Phase 002 begins** (D-08). Nothing here is invented from taste; nothing is deferred indefinitely.
3. **The Playwright visual-regression harness and the machine checks are contract-only** — specified in §11/§12, implemented in Phase 002 (D-17, D-18).

### 0.1 D-01 reconciliation (explicit, load-bearing)

`PRODUCT-MASTER-SPEC.md` §2.2 lists "dark olive / khaki structural framing and navigation areas" as a color family. **A literal dark-frame reading is overridden by D-01**: all three binding primaries render frame and navigation as a **light warm-gray with an olive undertone** — never a dark surface. The reason the spec text and the images disagree: §2.2 describes the *family's hue neighborhood* (olive/khaki), while the primaries render that family at high lightness. The only dark **structural** surface in the entire asset set is the old implementation's charcoal bezel in `patient-tracking-dashboard.jpg` — diagnostic evidence of the §3.7 color failure, never design intent. Two contained dark elements inside binding primaries — the timeline scrubber's dark viewport window (§10.2, an overlay control per D-03) and the patient-home device-mockup bezel (a presentation artifact of the mockup, not app chrome) — do not authorize any later phase "restoring" a dark frame or dark navigation. The constitution must repeat this reconciliation verbatim in intent.

| Property | Value |
|----------|-------|

### 1.1 Design-system core + per-surface grammar (D-15)

This contract is structured as **one shared design-system core** (§3–§9: tokens, geometry, typography, depth, motion, responsive) **plus one per-surface grammar section per binding primary** (§10). Every later phase cites the section for its surface; no phase invents a second design language.

### 1.2 Source-of-truth hierarchy (§1 of the spec — the constitution records this)

Constitution → primary reference image → reference UI specification + UI invariants → phase spec → technical plan → tasks → existing repository → agent preference. The repository is **never** a higher authority than approved design/specification.

### 1.3 What is binding vs. what is never copied

Binding from the primaries: layout, geometry, density, proportion, interaction patterns, color *relationships*. Never copied (D-13, §3.3): sample clinical content — see the do-not-reuse list in §13.

### 1.4 Hex provenance and review protocol (D-08)

All hex values in this contract were derived on 2026-10-05 by **ffmpeg region-average pixel sampling** (4–24px windows, scale-to-1×1, `rgb24`) of the three binding primaries, with sample locations located by a vision pass over each image and verified by grid scans. Values marked *(vision-estimate)* were not reliably pixel-sampled (thin strokes, antialiasing) and are weaker evidence. **Every value in §4 and §14 must be re-sampled during Phase 1 execution, tabulated with its derivation, and visually approved by the product owner at the design gate before Phase 002.** Measured caveat to resolve at that gate: the sampled light grays read near-neutral with a very slight cool bias in the blue channel (e.g. `#E0E3E8`, `#F1F4F8`), while D-01 characterizes the frame as warm-gray with an olive undertone; the owner's visual review fixes the final undertone so the frozen tokens carry the intended cast. The load-bearing part of D-01 — **light, never dark** — is decisively confirmed by measurement.

## 2. Spacing Scale

Declared values (multiples of 4px), tuned to the reference's compact clinical rhythm (§3.8, D-09):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, pill inner horizontal padding halves, timeline node-to-label offset |
| sm | 8px | Compact control padding-y, chip gaps, status pill insets, stat-row gaps |
| md | 12px | Compact control padding, folder-card row spacing, timeline micro-card padding |
| lg | 16px | Dense clinical card inner padding (provider + workspace surfaces), list row padding |
| xl | 24px | Section padding, card-to-card gaps, panel padding (patient home cards) |
| 2xl | 32px | Major layout gaps, patient-home generous card padding (upper end of the rhythm) |

Exceptions: touch targets on mobile are ≥44px in both axes (§8, §26 — target size, not spacing); patient home deliberately uses the upper end (xl–2xl) of the same scale to achieve lower density; provider/workspace surfaces use xs–lg inside cards. No spacing value outside this scale; no page-level 48/64px breaks — the reference keeps compact rhythm throughout. **Provisional, flagged for owner review against the measured reference density.**

## 3. Typography

Exactly four sizes, two weights, per the reference's hierarchy (large tabular stat values → card titles → body/secondary; compact clinical rhythm):

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Display / stat value | 28px | 600 (semibold) | 1.1 — tabular numerals mandatory |
| Heading / card + section title | 16px | 600 (semibold) | 1.25 |
| Body | 14px | 400 (regular) | 1.5 |
| Label / secondary / axis | 12px | 400 (regular) | 1.4 |

Eyebrow style (reference: "MEDICATION REMINDER:") = the 12px label at 500 is **not** allowed — weights are exactly 400 and 600; eyebrows render as the 12px/400 label with `text-transform: uppercase` and `letter-spacing: 0.08em`. Body minimum for any non-decorative text is 12px. Titles the vision pass read as "bold" are **600 at the declared sizes** — do not add a 700 weight. **Provisional (ratio-derived from the reference's measured hierarchy), flagged for owner review.**

### 4.3 Accent split rule (D-02 — locked decision rule, provisional outcome)

D-02: `accent` is the chartreuse sampled from the timeline event nodes, and the family is **not** split into `accent` + `accentSoft` **unless pixel sampling proves the timeline yellow and the provider-home CTA yellow are two distinct hues**. Provisional sampling on 2026-10-05 indicates **they are distinct**: TL event nodes measure `#EDFE4F` (yellow-green chartreuse, high lightness) while the PH primary CTA pill measures `#FFCE04` (saturated golden yellow, ~20° hue apart and markedly deeper). Therefore:

- **Default (single token):** `accent` = `#EDFE4F`, and the PH CTA renders from the same family.
- **If the design gate confirms the split (current evidence says it will):** add exactly one token, `accentSoft` = `#FFCE04` (D-02's naming), mapped as: `accent` (chartreuse) → timeline event nodes, milestones, active-emphasis markers, key state indicators; `accentSoft` (golden) → primary CTA and key interaction buttons.
- The split is decided at the owner's design gate with both swatches laid against the images. No third yellow token, ever.

### 4.4 Accent reserved for (explicit list — never "all interactive elements")

Timeline event nodes and their count badges; timeline milestone markers; primary CTA (provider home hero action); active/selected emphasis markers (active chart-range toggle, selected scrubber range is *not* accent — it is the dark overlay window); key state indicator dots; important-interaction highlights. **Not** for: folder cards (status uses `success`/`info`/`warning` only, D-04), body text, borders, backgrounds, decorative fills, or every icon.

### 4.5 Multi-hue restriction (D-04 — locked)

Folder tab headers and status pills encode meaning with `success` / `info` / `warning` **only**. The pastel mint/lavender/blue/tan quick-log chips in `patient-home-primary.jpg` (measured: mint `#B4EAD3`, lavender `#99A5BD`, putty `#B6B5B1`) are **decorative icon tints and must be rendered from existing `canvas` / `surface` / `borderSubtle` tokens — no new tint family is added.** This is the concrete enforcement of §2.2's "never every folder a different saturated color."

### 4.6 Role-based contract (D-11)

Tokens are **role-based, not literal-value-based** — a dark-mode set can later be added without renaming any token. This phase ships light-only values; the reference grammar is a light-mode product. Dark values are deferred (see 01-CONTEXT.md Deferred Ideas).

## 6. Depth & Elevation (§2.4, D-03, D-05, D-09)

Exactly **two elevation levels**; shadows carry surface separation; **components never invent their own shadow values** (D-03). Tokenized in `tokens.json` → `shadow`:

| Token | Provisional value | Usage |
|-------|------------------|-------|
| `shadowRaised` | `0 2px 6px rgba(31,35,43,0.07), 0 8px 24px rgba(31,35,43,0.05)` | `surfaceRaised` — cards, modals; the soft neumorphic lift of the reference |
| `shadowOverlay` | `0 12px 32px rgba(31,35,43,0.16), 0 4px 12px rgba(31,35,43,0.10)` | The single overlay level — popovers, the scrubber viewport window |

`borderSubtle` is a **hairline used only for true dividers, table row lines, the timeline axis, and the scrubber track** (D-05). **No outlined-card look** — card edges separate by shadow, not border. The dark scrubber viewport window and the MRI event card render as the overlay level with a scrim derived from `textPrimary` (high opacity) — not a new color token. Avoid excessive glassmorphism and neumorphism that makes controls indistinguishable; the reference (soft outer shadow + faint inner light edge) is the authority, not the trend names. **Provisional, flagged for owner review.**

## 7. Motion Rules (§9, D-19 — tokenized, not merely qualitative)

Tokenized in `tokens.json` → `motion`:

| Token | Value | Usage |
|-------|-------|-------|
| `motionFast` | 120ms | Micro-interactions: hovers, toggles, pill state changes, badge changes |
| `motionSlow` | 240ms | Panels, surfaces, sheets, timeline choreography segments |

**Single easing set:** `easeStandard` = `cubic-bezier(0.2, 0, 0, 1)` (decelerate-out) for entrances/emphasis; `easeExit` = `cubic-bezier(0.4, 0, 1, 1)` for exits. No other curves.

**Two-layer architecture (locked):** Framer Motion (`motion` package) for component entrance/exit, layout transitions, panels, sheets, folder-to-workspace transitions, compact micro-interactions. GSAP only where genuinely advantageous: complex SVG drawing, timeline path animation, timeline choreography, advanced interaction sequences (scrubber-driven progressive rendering) — scoped via `gsap.context()` / `useGSAP()`. Do not automatically use both for every animation.

**All motion must be:** fast, smooth, subtle, interruptible, purposeful — never gamified. **Mandatory reduced-motion fallback:** every animation routes through `useReducedMotion` (Framer Motion) and `gsap.matchMedia('(prefers-reduced-motion: reduce)')` (GSAP), degrading to opacity-only transitions ≤120ms or a static render for timeline choreography. This is a written invariant Phase 002 must implement, not an aspiration.

## 8. Responsive Rules (§26)

Web and mobile share the design language but **not identical layouts**:

- **Desktop (≥1024px):** horizontal timeline; dense folder grid (3-column, per PH measurement); larger information surfaces; full compact clinical density; persistent left icon rail.
- **Tablet (768–1023px):** adapted column flow, same token set.
- **Mobile (<768px):** adapted for touch — targets ≥44px, compact navigation (horizontal scrolling pill tabs), reduced density (folder grid to 1–2 columns), reachable controls, safe interactions; the timeline and scrubber remain reachable and usable (§8.3, UX-05).
- **Do not simply shrink the desktop version.** Breakpoint behavior is part of the contract later phases are checked against; exact breakpoints are Phase 002 implementation detail within these bands.

## 9. Copywriting Contract

**Rules (binding on all later phases):** sentence case; no exclamation marks; calm clinical verbs; no gamified vocabulary (points, levels, streaks, rewards, celebration); no fabricated urgency; destructive or clinically significant actions always confirmed; every major workspace has deliberate loading/empty/error/retry/permission-denied/offline-sync states (§24) — no generic "Loading…" screens (token-derived skeletons instead), no blank panels; permission-denied copy explains what access is lacking **without leaking data existence** (UX-02).

**Defaults reserved for the owning phases (this phase ships no screens; these are the contract defaults, not implemented copy):**

| Element | Copy |
|---------|------|
| Primary CTA (Provider Home — Phase 004 owns final label) | Single verb + noun, e.g. "Add New Patient" — the reference's combined "Add New Patient or Scan AI OCR Prescription" pill is reference grammar (one gold pill, icon, dark text); the final split or combined label is decided at Phase 004 copy review. Never a vague "Get Started" |
| Empty state heading | "No {record-type} yet" |
| Empty state body | One line of what will appear here + one next step, e.g. "Records will appear here as care progresses." |
| Error state | Problem + path: "Couldn't load {surface}. Check your connection and try again." + a "Try again" action |
| Destructive confirmation | Clinical stops use the explicit verb: "{Verb} {thing}" as the confirmation heading, one consequence line, confirm button labeled with the verb itself (e.g. "Stop Lisinopril"). Never "OK/Cancel" for clinical actions |

**Do-not-reuse list (D-13 — sample content, never copied into the product):** patient names (Sarah Miller, Robert Garcia, Tiffany Woodward, Dr. Eleanor Vance, Dr. Smith, …), numeric IDs/MRNs, medications (Lisinopril 10mg, Metformin 500mg, …), the `Cardiology` label, the `Vital Signs` / `Communication` tabs, vitals values (72 bpm, 118/75, 98%, 36.8°C), lab names (CBC Panel, Lipid Profile, Glucose), appointment/sample rows, "Daily Stats" numbers. Layout, geometry, density, and interaction patterns are the binding grammar; sample content is not.

### 11.1 Playwright visual-regression harness contract (specified here, built in Phase 002 — D-18)

- **Viewports:** 1440×900 (canonical desktop), 1280×800, 768×1024 (tablet), 390×844 (mobile).
- **Baseline naming:** `tests/visual/baselines/{surface}/{viewport}/{state}.png` (e.g. `provider-home/1440x900/default.png`); states include `default` and `reduced-motion`.
- **Capture:** against a production build (`next build` + start), CSS animations disabled during capture, `prefers-reduced-motion` variant captured via emulation.
- **Tolerance:** `maxDiffPixelRatio: 0.01`, `threshold: 0.2` (per-pixel); any diff beyond tolerance fails the gate.
- **Baselines are committed** (not gitignored); regeneration is a deliberate `--update-snapshots` act recorded in the phase that regenerated it.

## 12. Machine-Check Contract (D-17 — named here, implemented in Phase 002)

Anti-drift is enforced in two layers: the prose rules above **and** these explicitly named machine checks, so Phase 002 implements exactly what this phase wrote:

1. **`no-raw-hex`** — no raw hex color literal outside the generated token layer (`tokens.json` → generated `tokens.css`/`@theme`); all component styling references semantic tokens.
